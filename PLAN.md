# План работ: этапы 0 и 1

Проект: **Elementary**. Основа: [ТЗ](TZ.md) v0.4.
Версия плана: 0.2 (01.10.2026). Архитектурные решения для MVP согласованы.

Этап 0 — подготовка: инструменты, репозитории, каркасы, автоматическая сборка.
Этап 1 — MVP: гость заходит по имени, создаёт комнату, друзья входят по ссылке, вместе проходят одно дело от предыстории до финала. Всё развёрнуто в Yandex Cloud по HTTPS.

Остальные этапы будут детализированы, когда дойдём до них.

## Архитектурные решения для MVP

1. **Комнаты живут в game-service.** Зал ожидания и партия — это одна WebSocket-сессия, поэтому комната от создания до финала принадлежит игровому сервису. Лобби (этап 2) станет каталогом открытых комнат: поиск, фильтры, список. Оно будет узнавать о комнатах из событий game-service через RabbitMQ.
2. **В MVP нет PostgreSQL и RabbitMQ.** Гостям не нужна база (их данные лежат в токене), событиям пока некому уходить. Оба компонента появятся на этапе 2 вместе с регистрацией и лобби. Меньше движущихся частей — быстрее первая партия.
3. **Токены JWT подписывает user-service** закрытым ключом (RS256). Остальные сервисы проверяют подпись открытым ключом, не обращаясь к user-service на каждый запрос.
4. **game-core — чистая Java-библиотека без Spring.** Все правила, проверки и сокрытие информации живут там и покрываются тестами. game-service лишь доставляет команды в ядро и рассылает результат.
5. **Сервер отправляет каждому игроку его личное представление состояния** (свою руку, но не чужие). Скрытые карты никогда не попадают в браузер, поэтому их нельзя подсмотреть через инструменты разработчика.
6. **Дело в MVP — файл** в репозитории `cases`. Сервис контента и редактор появятся на этапе 3.
7. **Сервер в облаке — одна виртуальная машина** с Docker Compose. Caddy выдаёт HTTPS-сертификат автоматически, раздаёт фронтенд и изображения, проксирует запросы в шлюз.

# Этап 0. Подготовка

### И1. Установить инструменты разработчика

Создать на GitHub организацию `elementary-game` (или другое имя), чтобы все репозитории жили вместе. Договориться о правилах и записать их в `docs/CONTRIBUTING.md`:
- ветка `main` всегда рабочая, изменения вносятся через ветки вида `feature/Я4-turn-actions` и Pull Request;

**Готово, когда:** организация создана, правила записаны, в настройках `main` включена защита от прямых коммитов.

### И2. Локальное окружение на Docker Compose

Создать репозиторий `infra` с файлом `local/docker-compose.yml`, который поднимает Redis (с включённым AOF, чтобы данные переживали перезапуск) и Redis Insight для просмотра содержимого. Позже сюда добавятся PostgreSQL и RabbitMQ.

**Изучить:** Docker Compose, тома (volumes), Redis persistence (RDB и AOF).

### Я1. Каркас игрового ядра

Создать Maven-проект без Spring: Java 25, JUnit 5, AssertJ. Пакеты: `model` (данные), `engine` (правила), `view` (представление для игрока), `error` (ошибки правил). Один тест-пустышка.

**Готово, когда:** `mvn verify` проходит, тест запускается.

**Готово, когда:** сервис запускается локально и подключается к Redis из И2, `/actuator/health` отвечает `UP`.

**Изучить:** Spring Boot профили, Actuator.

### П1. Каркас сервиса пользователей
**Репозиторий:** `user-service` · **Зависит от:** А1

Аналогично Г1: Spring Boot, Web, Actuator, Security, Validation. Без базы данных.

**Готово, когда:** сервис запускается, `/actuator/health` отвечает `UP`.

### Ш1. Каркас шлюза
**Репозиторий:** `gateway` · **Зависит от:** А1

Spring Cloud Gateway (реактивный) с Actuator. Пока без маршрутов.

### Ф1. Каркас фронтенда
**Репозиторий:** `frontend` · **Зависит от:** А1

**Готово, когда:** `npm run dev` открывает приложение, переходы между заглушками работают, `npm run lint` и `npm run build` проходят без ошибок.

### А2. Публикация game-core в GitHub Packages
**Репозиторий:** `game-core` · **Зависит от:** Я1

game-core нужен game-service как зависимость, а репозитории разные. Настроить публикацию артефакта в GitHub Packages (Maven) и подключение этого репозитория пакетов в game-service. Локально можно использовать `mvn install`.

**Готово, когда:** game-service собирается с game-core, скачанным из GitHub Packages.

**Изучить:** Maven `distributionManagement`, `settings.xml`, токены GitHub для пакетов, семантическое версионирование.

### А3. CI для Java-репозиториев
**Репозиторий:** `game-core`, `game-service`, `user-service`, `gateway` · **Зависит от:** А2

**Готово, когда:** PR с падающим тестом нельзя влить в `main`.

**Изучить:** GitHub Actions: workflow, jobs, `actions/setup-java`, кэш, секреты.

### А4. CI для фронтенда
**Репозиторий:** `frontend` · **Зависит от:** Ф1

GitHub Actions: `npm ci`, `lint`, проверка типов, `build`, запуск тестов (Vitest).

# Этап 1. MVP

## Контент

### К1. Формат файла дела
**Репозиторий:** `cases` · **Зависит от:** Т1

Описать формат дела в JSON и JSON Schema для проверки. Структура по ТЗ, раздел 5: метаданные, языки, предыстория (слайды: изображение, текст, аудио, видео, длительность), карты двух типов (номер, тип, изображение или фон, текст с **жирным**, подпись, относится ли к делу), вопросы (варианты, правильный), истинная картина со ссылками на карты. Тексты — по ключам языков (`"ru": "..."`). Решить, как в тексте размечается жирный (предлагаю `**...**`) и ссылки на карты (предлагаю `[[15]]`). Пути к файлам — относительные внутри папки дела.

**Готово, когда:** есть схема, пример-заглушка из 5 карт проходит проверку схемой, формат описан в `cases/README.md`.

**Изучить:** JSON Schema.

### К2. Перенести первое реальное дело
**Репозиторий:** `cases` · **Зависит от:** К1

Выбрать одно из готовых дел. Для текстовых карт — перепечатать текст и подготовить фоны без текста; для карт-картинок — подготовить изображения и подписи. Сжать изображения (WebP). Собрать предысторию: слайды и, при желании, аудиозапись. Заполнить вопросы и истинную картину.

**Готово, когда:** дело проходит проверку схемой и полностью играется в MVP.

**Совет:** это ручная работа, её удобно делать урывками, параллельно с программированием.

## Игровое ядро

### Я2. Модель данных
**Репозиторий:** `game-core` · **Зависит от:** Я1, К1

Описать неизменяемые (record) классы: `CaseDefinition` (то, что загружено из файла), `Card`, `Question`, `GameState` (фаза, игроки и порядок, руки, стол, основная колода, резерв, сброс, текущий ход, таймер, голосование, ответы), `Player` (id, имя, статус: в игре / отключён / вышел). Фазы: `PROLOGUE`, `PLAYING`, `NO_MOVES_LEFT`, `ANSWERING`, `FINISHED`.

**Готово, когда:** модель компилируется, ревью со мной пройдено.

**Изучить:** Java records, неизменяемость, sealed interfaces (пригодятся для команд и событий).

### Я3. Подготовка партии
**Репозиторий:** `game-core` · **Зависит от:** Я2

Функция `GameEngine.start(caseDef, players, settings, random)`: карта №1 на стол, перемешивание остальных, раздача (до 6 игроков — по 3, при 7–8 — по 2), случайный порядок ходов. Генератор случайных чисел передаётся снаружи, чтобы в тестах результат был предсказуемым.

**Готово, когда:** тесты проверяют раздачу для 1, 6 и 7 игроков, наличие карты №1 на столе, отсутствие дублей карт, детерминированность при одинаковом seed.

### Я4. Ход: выложить или сбросить
**Репозиторий:** `game-core` · **Зависит от:** Я3

Команды `PlayCard` и `DiscardCard`. Проверки: сейчас ход этого игрока, карта у него в руке, фаза `PLAYING`. Затем добор 1 карты и переход хода к следующему игроку со статусом «в игре». Когда колода, резерв и руки пусты — фаза `NO_MOVES_LEFT`. Нарушения правил возвращают понятную ошибку, а не исключение-сюрприз.

**Готово, когда:** тесты на каждое правило и каждую ошибку.

### Я9. Представление состояния для игрока
**Репозиторий:** `game-core` · **Зависит от:** Я4

Функция `view(state, playerId)`: возвращает только то, что игрок имеет право видеть (ТЗ, 4.6): свою руку, стол, количество карт у других, в колоде и сбросе, статусы, чей ход. Признак «относится к делу» и содержимое сброса — только в фазе `FINISHED`.

**Готово, когда:** тесты доказывают, что ни одна чужая или скрытая карта не попадает в представление.

**Почему это важно:** это главная защита от читов.

### Я5. Отключение, выход, резерв, возвращение
**Репозиторий:** `game-core` · **Зависит от:** Я4

Команды `PlayerDisconnectTimeout` (прошло 2 минуты), `PlayerLeft`, `PlayerReturned`. Карты ушедшего уходят в резерв с пометкой владельца. Добор: сначала основная колода, потом резерв. Возвращение: игрок забирает свои оставшиеся в резерве карты и снова участвует в очерёдности. Ходы отсутствующих пропускаются; если отсутствующий был текущим — ход переходит дальше.

**Готово, когда:** тесты на сценарии из ТЗ 4.4–4.5, включая двух ушедших одновременно и возвращение после того, как часть резерва уже разобрана.

### Я6. Таймер хода
**Репозиторий:** `game-core` · **Зависит от:** Я4

Команда `TurnTimeout`: если игрок не сходил, на стол выкладывается случайная карта из его руки. Ядро не считает время само: оно хранит, когда истекает ход, а сигнал об истечении приходит снаружи. Защита от устаревшего сигнала: команда содержит номер хода и игнорируется, если ход уже сменился.

**Готово, когда:** тесты на истечение, на устаревший сигнал, на партию без таймера.

### Я7. Голосование за финал
**Репозиторий:** `game-core` · **Зависит от:** Я4

Команды `StartVote`, `CastVote`. Большинство — больше половины игроков со статусом «в игре». Голосование завершается, когда большинство «за» достигнуто или успех стал невозможен. При успехе — фаза `ANSWERING`; при провале игра продолжается. Работает и в фазе `NO_MOVES_LEFT`. Решить со мной: что делать с голосованием, если во время него кто-то отключился.

**Готово, когда:** тесты для 1, 2, 4, 5 игроков и для случая с отключёнными.

### Я8. Финал и подсчёт очков
**Репозиторий:** `game-core` · **Зависит от:** Я7

Участники ответов — игроки «в игре» на момент перехода к ответам; вернувшийся до показа таблицы тоже может ответить. Команды `SubmitAnswers` (все ответы сразу) и `ForceResults` (кнопка хозяина). Когда ответили все участники — подсчёт очков (одинаковые очки за вопрос) и фаза `FINISHED`, в которой раскрываются истинная картина и сброс.

**Готово, когда:** тесты на подсчёт, на ожидание, на кнопку хозяина.

### Я10. Сценарий целой партии и сериализация
**Репозиторий:** `game-core` · **Зависит от:** Я8

Тест, проигрывающий партию на 4 игрока от старта до `FINISHED` с отключением, возвращением и голосованием. Проверка, что `GameState` превращается в JSON (Jackson) и обратно без потерь — это нужно для хранения в Redis. Опубликовать версию `0.1.0`.

**Готово, когда:** тест проходит, версия опубликована в GitHub Packages.

### Т2. Протокол игры
**Репозиторий:** `docs` · **Зависит от:** Я10

Описать все сообщения между браузером и game-service: адреса подписок, команды клиента, события сервера, формат ошибок, пример каждого сообщения. Это контракт для бэкенда и фронтенда.

**Готово, когда:** документ `docs/protocol.md` покрывает весь MVP.

## Пользователи и шлюз

### П2. Гостевой вход
**Репозиторий:** `user-service` · **Зависит от:** П1

`POST /api/auth/guest` с именем (проверка длины и символов) → JWT с `sub` = случайный guestId, именем и ролью `GUEST`, подписанный RS256. Ключ хранится вне кода (переменная окружения или файл).

**Готово, когда:** запрос возвращает токен, его содержимое проверяется на jwt.io.

**Изучить:** JWT, RS256, почему секрет не кладут в репозиторий.

### П3. Публикация открытого ключа
**Репозиторий:** `user-service` · **Зависит от:** П2

Эндпоинт `/.well-known/jwks.json` с открытым ключом, чтобы другие сервисы могли проверять токены.

**Готово, когда:** эндпоинт отдаёт ключ в формате JWKS.

### Ш2. Маршрутизация
**Репозиторий:** `gateway` · **Зависит от:** Ш1, П2

Маршруты: `/api/auth/**` → user-service, `/api/game/**` и `/ws/**` (WebSocket) → game-service. Настроить CORS для локальной разработки.

**Готово, когда:** гостевой вход и тестовый запрос в game-service работают через шлюз.

### Г2. Проверка токенов в game-service
**Репозиторий:** `game-service` · **Зависит от:** Г1, П3

Spring Security как resource server с проверкой JWT по JWKS. Для WebSocket — проверка токена при подключении (STOMP CONNECT), игрок определяется по токену, а не по данным из сообщений.

**Готово, когда:** запросы и подключения без токена или с поддельным токеном отклоняются.

## Игровой сервис

### Г3. Загрузка дел
**Репозиторий:** `game-service` · **Зависит от:** Г1, К1

Загрузка дел из папки (путь в настройках) при старте, проверка, превращение в `CaseDefinition`. `GET /api/game/cases` — список дел для выбора в комнате.

**Готово, когда:** сервис отдаёт список с делом-заглушкой из К1.

### Г4. Комнаты
**Репозиторий:** `game-service` · **Зависит от:** Г3

REST: создать комнату (дело, лимит игроков, таймер хода, язык) → короткий код комнаты; получить информацию по коду; войти по коду. Создатель — хозяин: может исключить игрока и запустить игру при любом числе игроков. Комнаты хранятся в Redis, заброшенные удаляются по истечении срока (TTL).

**Готово, когда:** через REST-клиент (например, IntelliJ HTTP Client) можно пройти сценарий «создал → двое вошли → один исключён → запуск».

### Г5. WebSocket-подключение
**Репозиторий:** `game-service` · **Зависит от:** Г2, Г4

STOMP поверх WebSocket. Подписки: `/topic/room.{code}` (общие события) и личная очередь `/user/queue/state` (личное представление). Команды клиента приходят на `/app/room.{code}/...`.

**Готово, когда:** два браузерных клиента (или тестовых) получают события комнаты.

**Изучить:** STOMP, Spring WebSocket message broker, `@MessageMapping`.

### Г6. Хранение партий в Redis
**Репозиторий:** `game-service` · **Зависит от:** Я10, Г4

Репозиторий партий: сохранение и загрузка `GameState` в JSON. Команды одной партии обрабатываются строго по очереди (блокировка на партию), чтобы два одновременных хода не испортили состояние.

**Готово, когда:** после перезапуска сервиса партия загружается из Redis в том же состоянии; тест с параллельными командами не ломает состояние.

### Г7. Обработка игровых команд
**Репозиторий:** `game-service` · **Зависит от:** Г5, Г6

Цепочка: команда из WebSocket → загрузить состояние → game-core → сохранить → разослать каждому игроку его представление (Я9). Ошибки правил — только отправителю.

**Готово, когда:** партию можно сыграть через тестовых клиентов от старта до финала.

### Г10. Подключения и переподключения
**Репозиторий:** `game-service` · **Зависит от:** Г7

Отслеживать подключение и отключение игроков (события сессий STOMP). При отключении — статус «отключён» и запуск 2-минутного таймера; при повторном подключении — `PlayerReturned` и отправка текущего состояния. Игрок с несколькими вкладками не должен ломать логику.

**Готово, когда:** закрыл вкладку → остальные видят «отключён»; открыл снова → вернулся со своими картами.

### Г9. Таймеры, переживающие перезапуск
**Репозиторий:** `game-service` · **Зависит от:** Г10

Таймеры отключения и хода: сроки хранятся в Redis (например, в sorted set по времени), планировщик раз в секунду забирает истёкшие и отправляет команды в ядро. После перезапуска сервиса таймеры продолжают работать.

**Готово, когда:** таймер хода срабатывает, в том числе если сервис перезапустили во время ожидания.

### Г8. Синхронная предыстория
**Репозиторий:** `game-service` · **Зависит от:** Г7

В фазе `PROLOGUE` сервер объявляет момент начала показа; клиенты сами вычисляют текущий слайд по времени (так все видят одно и то же, а сервер не шлёт событие на каждый слайд). Команды «Готов» и «Начать» (хозяин). Опоздавший игрок попадает на текущий слайд.

**Готово, когда:** в двух браузерах слайды листаются синхронно, после «Готов» от всех начинается игра.

## Облако

### И3. Домен
**Репозиторий:** — · **Зависит от:** —

Купить домен, делегировать DNS в Yandex Cloud DNS (или оставить у регистратора), создать запись A на будущий IP сервера.

**Готово, когда:** домен указывает на IP виртуальной машины.

### И4. Виртуальная машина в Yandex Cloud
**Репозиторий:** `infra` · **Зависит от:** И1

Аккаунт и платёжный аккаунт, каталог для проекта, бюджет с уведомлением (чтобы не выйти за 5000 ₽), статический IP, виртуальная машина Ubuntu (на старте хватит 2 vCPU и 4 ГБ памяти, можно прерываемую для тестов), группа безопасности: открыты только 22, 80, 443. Вход по SSH-ключу, вход по паролю отключён, установлен Docker. Шаги записать в `infra/README.md`.

**Готово, когда:** можно зайти по SSH и запустить `docker run hello-world`.

**Изучить:** группы безопасности, SSH-ключи, базовая настройка Ubuntu (обновления, firewall).

### И5. Docker-образы
**Репозиторий:** все сервисы и `frontend` · **Зависит от:** Г7, П2, Ш2, Ф6

Многоэтапные Dockerfile: сборка в одном образе, запуск в лёгком образе только с JRE. Для фронтенда — сборка статики. Настройки через переменные окружения.

**Готово, когда:** образы собираются, весь проект запускается локально одним `docker compose` из образов.

**Изучить:** multi-stage builds, почему не стоит запускать процесс от root в контейнере.

### И6. Боевое окружение на сервере
**Репозиторий:** `infra` · **Зависит от:** И3, И4, И5

`prod/docker-compose.yml`: Redis, user-service, game-service, gateway, Caddy. Caddy получает HTTPS-сертификат, раздаёт статику фронтенда и файлы дел, проксирует `/api` и `/ws` в шлюз. Секреты (ключ JWT) — в файле `.env` на сервере, не в Git. Только Caddy доступен снаружи.

**Готово, когда:** `https://ваш-домен` открывает игру, в браузере зелёный замок.

### А5. Автоматический деплой
**Репозиторий:** все сервисы, `frontend`, `infra` · **Зависит от:** И6, А3, А4

При push в `main`: сборка образа → публикация в GitHub Container Registry → подключение к серверу по SSH → `docker compose pull && docker compose up -d`. SSH-ключ деплоя — в секретах GitHub.

**Готово, когда:** вливание PR в `main` через несколько минут меняет версию на сервере без ручных действий.

**Изучить:** GHCR, секреты GitHub Actions, отдельный пользователь для деплоя на сервере.
