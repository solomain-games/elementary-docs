# Протокол игры

Контракт между браузером и бэкендом Elementary для MVP (этап 1): какие запросы и сообщения бывают, в каком формате и в каком порядке. Бэкенд и фронтенд реализуются по этому документу; любое изменение протокола сначала вносится сюда.

Версия протокола: **1**. Основа: [ТЗ](TZ.md) v0.7, `game-core` 0.1.0.

## 1. Общая схема

```
Браузер ──HTTPS──▶ Caddy ──▶ gateway :8080 ─┬─ /api/auth/**  ──▶ user-service
                                            ├─ /api/game/**  ──▶ game-service
                                            └─ /ws  (WebSocket) ─▶ game-service
        ◀── статика: /  (фронтенд),  /cases/{caseId}/**  (изображения и медиа дел)
```

| Что | Как | Зачем |
|---|---|---|
| Вход гостя, выбор дела, создание комнаты и вход в неё | **REST** (JSON по HTTP) | разовые действия «запрос — ответ» |
| Всё, что происходит в комнате и партии | **STOMP поверх WebSocket** | сервер сам присылает обновления всем игрокам |

**Принцип синхронизации: снимки состояния.** После любого изменения сервер присылает каждому участнику комнаты **полный снимок** — всё, что этот игрок должен видеть, — в его личную очередь. Клиент не собирает состояние из отдельных событий, а просто заменяет старый снимок новым. Так клиент не может «разойтись» с сервером, а переподключение не требует особой логики: после подключения сервер присылает свежий снимок.

События в общем канале комнаты (раздел 5.4) — только подсказки для анимаций и уведомлений. Истина — всегда снимок.

## 2. Соглашения

- Кодировка UTF-8, формат JSON, имена полей в `camelCase`.
- Время — строка ISO 8601 в UTC: `"2026-10-01T12:00:00Z"`.
- Длительности — целые секунды в полях с суффиксом `Seconds`.
- Отсутствующее значение — `null` (поле присутствует).
- Тексты дел приходят как объект переводов `{"ru": "..."}` (`LocalizedText`); клиент берёт значение по языку комнаты. Так формат совпадает с файлом дела и ядром.
- Разметка в текстах дел: `**жирный**`, `__подчёркнутый__`, `[[15]]` — ссылка на карту №15, `\n` — перенос строки. Разбирает клиент.
- Пути к файлам дела (`image`, `background`, `cover`, слайды) — относительные внутри папки дела. Полный адрес: `/cases/{caseId}/{путь}`.
- Идентификаторы игроков — строки из токена (`sub`). Клиент никогда не передаёт «от чьего имени» действие: сервер берёт игрока из токена.

## 3. Аутентификация

### 3.1. Гостевой вход

```http
POST /api/auth/guest
Content-Type: application/json

{ "name": "Анна" }
```

Имя: 1–24 символа, буквы, цифры, пробел, `-`, `_`; пробелы по краям обрезаются.

Ответ `200 OK`:

```json
{
  "token": "eyJhbGciOiJSUzI1NiIsImtpZCI6IjEifQ...",
  "expiresAt": "2026-10-02T12:00:00Z",
  "user": { "id": "g-6f1c2a9e", "name": "Анна", "role": "GUEST" }
}
```

Токен — JWT, подписанный user-service (RS256, ADR 0003). Поля: `sub` — id игрока, `name`, `role`, `exp`. Клиент хранит токен в `localStorage`, чтобы после перезагрузки остаться тем же гостем.

### 3.2. Передача токена

- **REST:** заголовок `Authorization: Bearer <token>` во всех запросах, кроме входа.
- **WebSocket:** заголовок `Authorization: Bearer <token>` в кадре STOMP `CONNECT` (браузер не позволяет задать заголовки самому WebSocket-рукопожатию, поэтому токен передаётся на уровне STOMP).

Просроченный или поддельный токен: REST — `401`; WebSocket — кадр `ERROR` и разрыв соединения. Клиент в этом случае заново выполняет гостевой вход.

### 3.3. Открытый ключ (для сервисов)

`GET /.well-known/jwks.json` в user-service — открытый ключ в формате JWKS. Используется game-service, браузеру не нужен.

## 4. REST

Базовый путь игрового сервиса: `/api/game`. Все запросы требуют токен.

### 4.1. Ошибки REST

Формат **Problem Details** (RFC 9457), плюс машинный код `code`:

```json
{
  "type": "about:blank",
  "title": "Conflict",
  "status": 409,
  "detail": "Room K7Q2PX is full",
  "code": "ROOM_FULL"
}
```

Клиент показывает пользователю текст по `code` из своих переводов, `detail` — только для отладки.

| HTTP | `code` | Когда |
|---|---|---|
| 400 | `VALIDATION_FAILED` | неверные поля запроса (дополнительно поле `errors`: `[{ "field": "name", "message": "..." }]`) |
| 401 | `UNAUTHORIZED` | нет токена или он недействителен |
| 403 | `NOT_HOST` | действие доступно только хозяину комнаты |
| 403 | `NOT_IN_ROOM` | игрок не состоит в комнате |
| 404 | `CASE_NOT_FOUND` | нет такого дела |
| 404 | `ROOM_NOT_FOUND` | нет комнаты с таким кодом (или она удалена по сроку) |
| 409 | `ROOM_FULL` | в комнате нет мест |
| 409 | `GAME_ALREADY_STARTED` | в идущую партию войти нельзя (вернуться можно только участнику) |
| 409 | `LANGUAGE_NOT_SUPPORTED` | у дела нет перевода на язык комнаты |

### 4.2. Список дел

```http
GET /api/game/cases
```

```json
[
  {
    "id": "demo",
    "title": { "ru": "Пропавший браслет" },
    "summary": { "ru": "Учебное дело из пяти карт." },
    "cover": "images/cover.webp",
    "languages": ["ru"],
    "recommendedPlayers": { "min": 1, "max": 4 },
    "durationMinutes": 10
  }
]
```

### 4.3. Предыстория дела

```http
GET /api/game/cases/{caseId}/prologue
```

Предыстория не секретна, её можно загрузить заранее, ещё в зале ожидания.

```json
{
  "slides": [
    {
      "image": "images/prologue-1.webp",
      "text": { "ru": "Утром в особняке Морозовых обнаружили пропажу **фамильного браслета**." },
      "audio": null,
      "video": null,
      "durationSeconds": 6
    }
  ]
}
```

`durationSeconds` сервер заполняет всегда: если в деле длительность берётся из аудио или видео, сервер подставляет их длину. Это нужно для синхронного показа (раздел 6).

### 4.4. Создать комнату

```http
POST /api/game/rooms

{ "caseId": "demo", "language": "ru", "maxPlayers": 6, "turnTimeoutSeconds": 60 }
```

| Поле | Значения |
|---|---|
| `maxPlayers` | 1–8 |
| `turnTimeoutSeconds` | `null` (без таймера), `30`, `60`, `120` |

Ответ `201 Created`, заголовок `Location: /api/game/rooms/K7Q2PX`:

```json
{ "code": "K7Q2PX" }
```

Создатель становится хозяином и сразу состоит в комнате. Код — 6 символов из `A–Z` и `2–9` без похожих (`0/O`, `1/I`). Ссылка-приглашение: `https://{домен}/room/K7Q2PX`.

### 4.5. Информация о комнате

```http
GET /api/game/rooms/{code}
```

Открытые сведения — чтобы показать экран «Войти в комнату» до входа:

```json
{
  "code": "K7Q2PX",
  "caseId": "demo",
  "caseTitle": { "ru": "Пропавший браслет" },
  "language": "ru",
  "players": 3,
  "maxPlayers": 6,
  "status": "WAITING"
}
```

`status`: `WAITING` — зал ожидания, `IN_GAME` — партия идёт, `FINISHED` — партия завершена.

### 4.6. Войти, выйти, исключить, начать

| Запрос | Кто | Ответ |
|---|---|---|
| `POST /api/game/rooms/{code}/join` | любой | `204`; если уже в комнате — тоже `204` (повторный вход безопасен) |
| `POST /api/game/rooms/{code}/leave` | участник | `204`. В зале ожидания — уход из комнаты; в партии — «Выйти» (ТЗ 4.5) |
| `POST /api/game/rooms/{code}/kick` `{ "playerId": "g-..." }` | хозяин | `204`. Только в зале ожидания |
| `POST /api/game/rooms/{code}/start` | хозяин | `204`. Раздача и начало предыстории при любом числе игроков (ТЗ 4.1) |

Если хозяин покидает зал ожидания, хозяином становится игрок, вошедший раньше всех из оставшихся. Пустая комната удаляется.

Результат всех этих действий участники видят в очередном снимке по WebSocket.

## 5. WebSocket (STOMP)

### 5.1. Подключение

Адрес: `wss://{домен}/ws` (локально через прокси Vite: `ws://localhost:5173/ws`).

Кадр `CONNECT`:

```
CONNECT
accept-version:1.2
heart-beat:10000,10000
Authorization:Bearer eyJhbGciOi...
X-Client-Version:0.1.0
```

- `heart-beat` — обмен пульсом каждые 10 секунд: так сервер быстро замечает обрыв связи (отключение игрока, ТЗ 4.5).
- `X-Client-Version` — версия фронтенда. Если сервер считает её устаревшей, он отвечает кадром `ERROR` с `message:CLIENT_OUTDATED`; клиент просит пользователя перезагрузить страницу (ТЗ 11).

### 5.2. Подписки

| Адрес подписки | Что приходит |
|---|---|
| `/user/queue/state` | личные **снимки** комнаты и партии (раздел 5.3) |
| `/user/queue/errors` | ответы на **свои** отклонённые команды (раздел 5.6) |
| `/topic/room.{code}` | общие **события** комнаты для анимаций и уведомлений (раздел 5.4) |

Сразу после подписки на `/user/queue/state` клиент отправляет команду `sync` (раздел 5.5) и получает актуальный снимок. Так же он поступает после каждого переподключения.

Если игрок открыл комнату в нескольких вкладках, снимки получают все вкладки; «отключённым» он считается, только когда закрыты все.

### 5.3. Снимок

Приходит в `/user/queue/state` после любого изменения комнаты или партии, отдельно каждому участнику — у каждого своё содержимое.

```json
{
  "protocolVersion": 1,
  "version": 57,
  "serverTime": "2026-10-01T12:00:14.250Z",
  "room": {
    "code": "K7Q2PX",
    "caseId": "demo",
    "language": "ru",
    "maxPlayers": 6,
    "turnTimeoutSeconds": 60,
    "hostId": "g-6f1c2a9e",
    "status": "IN_GAME",
    "members": [
      { "id": "g-6f1c2a9e", "name": "Анна", "online": true },
      { "id": "g-0b7d31c4", "name": "Борис", "online": true }
    ],
    "prologue": null
  },
  "game": { "...": "PlayerView, см. ниже" }
}
```

| Поле | Смысл |
|---|---|
| `version` | номер снимка комнаты, растёт с каждым изменением. Клиент **игнорирует** снимок с номером меньше уже полученного — так снимки, пришедшие не по порядку, не откатят состояние |
| `serverTime` | время сервера в момент отправки. Клиент вычисляет поправку `serverTime − своё время` и использует её для таймеров (раздел 7) |
| `room.members` | все, кто в комнате, в порядке входа; `online` — есть ли активное подключение |
| `room.prologue` | синхронный показ предыстории (раздел 6); `null`, если сейчас не предыстория |
| `game` | представление партии для этого игрока; `null` в зале ожидания |

#### `game` — представление партии (`PlayerView`)

Строится ядром (`PlayerViews.of`) и содержит только то, что игрок имеет право видеть (ТЗ 4.6, ADR 0005).

```json
{
  "caseId": "demo",
  "phase": "PLAYING",
  "viewerId": "g-6f1c2a9e",
  "hand": [
    { "number": 3, "image": "cards/03.webp", "caption": { "ru": "Следы земли на ковре" } },
    { "number": 4, "background": "backgrounds/paper.webp",
      "text": { "ru": "Записка в кармане гостьи:\n__Встретимся у ломбарда__ в **10 утра**" },
      "align": "CENTER" }
  ],
  "table": [
    { "number": 1, "image": "cards/01.webp", "caption": { "ru": "Пустая шкатулка в спальне" } }
  ],
  "players": [
    { "id": "g-6f1c2a9e", "name": "Анна", "status": "ACTIVE", "handSize": 2 },
    { "id": "g-0b7d31c4", "name": "Борис", "status": "DISCONNECTED", "handSize": 3 }
  ],
  "currentPlayerId": "g-6f1c2a9e",
  "deckSize": 12,
  "discardSize": 1,
  "turnNumber": 4,
  "turnDeadline": "2026-10-01T12:01:10Z",
  "vote": null,
  "answering": null,
  "reveal": null
}
```

| Поле | Смысл |
|---|---|
| `phase` | `PROLOGUE`, `PLAYING`, `NO_MOVES_LEFT`, `ANSWERING`, `FINISHED` |
| `hand`, `table` | лица карт. Карта-картинка: `number`, `image`, `caption` (может быть `null`). Текстовая: `number`, `background`, `text`, `align` (`LEFT`, `CENTER`, `RIGHT`, `JUSTIFY`). Тип различается по наличию поля `image` или `background` |
| `players` | все игроки партии **в порядке ходов**; `status`: `ACTIVE`, `DISCONNECTED`, `LEFT` |
| `currentPlayerId` | чей ход; `null`, если фаза не `PLAYING` |
| `deckSize` | сколько осталось добрать (основная колода и резерв вместе) |
| `turnDeadline` | когда истекает ход; `null` без таймера |
| `vote` | текущее голосование (ниже) или `null` |
| `answering` | вопросы и ход ответов; только в `ANSWERING` и `FINISHED` |
| `reveal` | раскрытие; только в `FINISHED` |

`vote`:

```json
{
  "initiatorId": "g-6f1c2a9e",
  "votes": { "g-6f1c2a9e": true, "g-0b7d31c4": false },
  "deadline": "2026-10-01T12:05:30Z",
  "votesNeeded": 2
}
```

`answering`:

```json
{
  "questions": [
    { "id": "culprit", "text": { "ru": "Кто взял браслет?" },
      "options": [ { "id": "owner", "text": { "ru": "Хозяйка" } }, { "id": "guest", "text": { "ru": "Гостья" } } ] }
  ],
  "participants": ["g-6f1c2a9e", "g-0b7d31c4"],
  "answered": ["g-6f1c2a9e"],
  "ownAnswers": { "culprit": "guest" }
}
```

Правильных ответов в `questions` нет. Чужие ответы не передаются — только список тех, кто ответил.

`reveal` (фаза `FINISHED`):

```json
{
  "discard": [ { "number": 5, "background": "backgrounds/receipt.webp", "text": { "ru": "Чек..." }, "align": "LEFT" } ],
  "allCards": [ { "number": 1, "image": "cards/01.webp", "caption": { "ru": "..." } }, "...все карты дела..." ],
  "relevantCards": [1, 2, 4],
  "solution": { "ru": "Гостья забрала браслет из шкатулки ([[1]])..." },
  "correctAnswers": { "culprit": "guest", "motive": "debt" },
  "scores": { "g-6f1c2a9e": 2, "g-0b7d31c4": 1 }
}
```

`allCards` — лица всех карт дела. Голосование может пройти, когда часть карт ещё в колоде или в руках, а истинная картина ссылается на любые карты (`[[15]]`): по клику клиент показывает карту из `allCards`.

### 5.4. События комнаты

Приходят в `/topic/room.{code}` всем участникам. Формат: `{ "type": "...", ...поля }`. Нужны для анимаций и всплывающих уведомлений; клиент может их игнорировать — состояние всё равно придёт снимком.

| `type` | Поля | Когда |
|---|---|---|
| `PLAYER_JOINED` | `playerId`, `name` | вошёл в зал ожидания |
| `PLAYER_LEFT_ROOM` | `playerId` | ушёл из зала ожидания |
| `PLAYER_KICKED` | `playerId` | исключён хозяином (исключённый получает это событие и перестаёт получать снимки) |
| `GAME_STARTED` | — | хозяин начал игру |
| `CARD_PLAYED` | `playerId`, `cardNumber`, `byTimer` | карта выложена на стол (`byTimer: true` — ход по истечении времени) |
| `CARD_DISCARDED` | `playerId` | карта сброшена (какая — не сообщается) |
| `PLAYER_DISCONNECTED` / `PLAYER_RECONNECTED` / `PLAYER_GAVE_UP` | `playerId` | изменение статуса в партии (`PLAYER_GAVE_UP` — вышел или не вернулся за 2 минуты) |
| `VOTE_STARTED` | `initiatorId` | начато голосование |
| `VOTE_PASSED` / `VOTE_FAILED` | — | итог голосования |
| `NO_MOVES_LEFT` | — | ходы закончились |
| `RESULTS_SHOWN` | — | подведены итоги |

### 5.5. Команды клиента

Отправляются кадром `SEND` на адрес `/app/room/{code}/{команда}`. В теле — JSON; поле `requestId` (любая уникальная строка, например UUID) необязательно, но если оно есть, сервер вернёт его в ответе об ошибке — так клиент поймёт, какая из его команд отклонена.

```
SEND
destination:/app/room/K7Q2PX/play
content-type:application/json

{"requestId":"b1f0c7d2","cardNumber":3}
```

| Команда | Тело | Фаза | Действие ядра |
|---|---|---|---|
| `sync` | `{}` | любая | прислать текущий снимок только этому игроку |
| `ready` | `{}` | `PROLOGUE` | «Готов» после предыстории (раздел 6) |
| `begin` | `{}` | `PROLOGUE` | хозяин: «Начать», не дожидаясь всех (раздел 6) |
| `play` | `{ "cardNumber": 3 }` | `PLAYING` | `PlayCard` |
| `discard` | `{ "cardNumber": 3 }` | `PLAYING` | `DiscardCard` |
| `startVote` | `{}` | `PLAYING`, `NO_MOVES_LEFT` | `StartVote` |
| `castVote` | `{ "inFavor": true }` | `PLAYING`, `NO_MOVES_LEFT` | `CastVote` |
| `submitAnswers` | `{ "answers": { "culprit": "guest", "motive": "debt" } }` | `ANSWERING` | `SubmitAnswers` |
| `forceResults` | `{}` | `ANSWERING` | хозяин: `ForceResults` |

Выход из партии — REST `POST /rooms/{code}/leave` (раздел 4.6), он работает и без WebSocket.

**Команды сервера, а не клиента.** Отключение и возвращение (`PlayerDisconnected`, `PlayerReturned`), истечение ожидания отключённого, хода и голосования (`PlayerDisconnectTimeout`, `TurnTimeout`, `VoteTimeout`), начало игры после предыстории (`BeginPlay`) game-service формирует сам — по событиям подключения и по таймерам. Клиент их отправить не может.

### 5.6. Ошибки команд

Отклонённая команда не меняет состояние; ответ приходит **только отправителю** в `/user/queue/errors`:

```json
{ "requestId": "b1f0c7d2", "command": "play", "code": "NOT_YOUR_TURN" }
```

Коды правил игры (из `game-core`, `RuleViolation`):

| `code` | Значение |
|---|---|
| `WRONG_PHASE` | команда недопустима в текущей фазе |
| `UNKNOWN_PLAYER` | игрока нет в партии |
| `NOT_YOUR_TURN` | сейчас ход другого игрока |
| `CARD_NOT_IN_HAND` | такой карты нет в руке |
| `INVALID_PLAYER_STATUS` | действие не подходит к статусу игрока |
| `VOTE_IN_PROGRESS` | голосование уже идёт |
| `NO_VOTE` | голосования нет |
| `ALREADY_VOTED` | уже проголосовал |
| `NOT_ELIGIBLE_TO_VOTE` | голосовать могут только игроки «в игре» |
| `NOT_ANSWER_PARTICIPANT` | игрок не участвует в ответах |
| `ALREADY_ANSWERED` | ответы уже отправлены |
| `INVALID_ANSWERS` | ответы не на все вопросы или с несуществующими вариантами |
| `NOT_HOST` | только для хозяина |

Коды протокола:

| `code` | Значение |
|---|---|
| `BAD_REQUEST` | тело команды не разобрано или в нём не хватает полей |
| `NOT_IN_ROOM` | отправитель не состоит в комнате |
| `ROOM_NOT_FOUND` | комнаты нет |
| `GAME_NOT_STARTED` | игровая команда в зале ожидания |
| `UNKNOWN_COMMAND` | нет такой команды |

Коды `NO_TURN_TIMER`, `STALE_TIMEOUT`, `TURN_NOT_EXPIRED`, `VOTE_NOT_EXPIRED` относятся к командам сервера и клиенту не приходят.

## 6. Предыстория

Предыстория показывается синхронно у всех без сообщения на каждый слайд (ТЗ 5.2, задача Г8):

1. Хозяин нажимает «Начать игру» (`POST /start`). Сервер раздаёт карты (фаза `PROLOGUE`) и назначает момент начала показа — через 3 секунды, чтобы все успели получить снимок.
2. В снимке появляется:

   ```json
   "prologue": {
     "startsAt": "2026-10-01T12:00:03Z",
     "readyPlayerIds": ["g-0b7d31c4"]
   }
   ```

3. Каждый клиент сам вычисляет текущий слайд: прошедшее время `serverNow − startsAt` раскладывается по `durationSeconds` слайдов (раздел 4.3). Опоздавший или переподключившийся игрок сразу попадает на текущий слайд.
4. После последнего слайда (или раньше) игрок нажимает «Готов» — команда `ready`. Хозяин может нажать «Начать» — команда `begin`.
5. Когда готовы все игроки «в игре» или хозяин нажал «Начать», сервер передаёт ядру `BeginPlay`: фаза `PLAYING`, `prologue` в снимке становится `null`.

Звук: браузеры запрещают запускать аудио без действия пользователя, поэтому клиент включает звук предыстории только после клика (кнопка «Начать прослушивание» или «Готов» в зале ожидания — задача Ф7).

## 7. Время и таймеры

- Сроки (`turnDeadline`, `vote.deadline`, `prologue.startsAt`) — моменты времени по часам **сервера**.
- Часы игрока могут отличаться от серверных на секунды. Клиент хранит поправку `offset = serverTime − Date.now()` из последнего снимка и показывает обратный отсчёт как `deadline − (Date.now() + offset)`.
- Сервер отправляет сигнал об истечении хода с запасом около 1 секунды после срока (задача Г9), чтобы ход, отправленный в последний момент, успел дойти.
- Если ход игрока и сигнал таймера пришли почти одновременно, сервер обрабатывает их строго по очереди; второй будет отклонён (`NOT_YOUR_TURN` для игрока), и в снимке будет видно, что произошло.

## 9. Изменение протокола

- Новое необязательное поле в ответе или снимке — совместимое изменение: старый клиент его игнорирует.
- Удаление или переименование поля, изменение смысла — несовместимое: увеличивается `protocolVersion`, сервер начинает отвечать `CLIENT_OUTDATED` старым клиентам.
- Любое изменение сначала вносится в этот документ, затем в код бэкенда и фронтенда.
